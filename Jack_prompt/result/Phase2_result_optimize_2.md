## 3. Root Cause

1. **การซักประวัติเป็นเพียง "คำแนะนำใน prompt"** -- รอบก่อนส่งบันทึก "ข้อมูลขั้นต่ำที่ขาด" ให้ LLM ตัดสินใจเอง ซึ่ง LLM มีแรงจูงใจจะตอบให้ครบ
   จึงข้ามไปตอบเสมอ **แก้ที่ prompt อย่างเดียวไม่พอ ต้องเป็นกฎที่บังคับได้ (deterministic gate)**
2. **เกณฑ์ "ข้อมูลขั้นต่ำ" เดิมแคบกว่า pattern ของผู้ใช้** (ไม่รวม Severity เช่นลักษณะการไอ/น้ำมูก, Any treated, Comorbidity, เกณฑ์ Centor ที่ยังไม่ทราบ)
3. **LLM รวมเลขคะแนนพลาดและเติมข้อที่ไม่รู้เอง** -- การให้ "ตารางเกณฑ์" อย่างเดียวไม่พอ ต้องคำนวณให้เสร็จแล้วส่งผลลัพธ์ไปให้
4. **prompt เดิมกำหนด "2-4 ตัวต่อกลุ่ม"** -> จำกัดความหลากหลายเอง และไม่มีการจัดลำดับ (ยาหลัก vs ผลิตภัณฑ์) กับไม่มีแนวคิดเรื่องความละเอียดของคำตอบ
5. **รูปแบบยาไม่ได้ถูกใช้เป็นข้อมูล** -- ตาราง Dose บอกอยู่แล้วว่าตัวไหนเป็นยาพ่น/ยาอม/ยากลั้วคอ แต่ระบบไม่เคยดึงมาใช้ตรวจชื่อหมวด
6. **ฝั่งเว็บไม่มีสไตล์สำหรับ Expert Opinion** -- บล็อกนี้ถูกเรนเดอร์เป็นหัวข้อธรรมดา กลืนกับเนื้อหา Guideline

## 4. ทางเลือก -> Best Solution

| ทางเลือก | ข้อดี | ข้อเสีย | ตัดสิน |
|---|---|---|---|
| A. เขียน prompt ย้ำให้ถามก่อน | ง่าย ไม่แตะโค้ด | **เป็นปัญหาเดิมที่พิสูจน์แล้วว่าไม่ได้ผล** (LLM ยังตอบต่อ) | ไม่พอ |
| B. ให้ LLM ตัดสินเองว่าจะถามไหม ผ่าน tool/function call | ยืดหยุ่น | +1 API call/คำถาม, ยังไม่แน่นอน, ต้องรื้อ pipeline | ไม่คุ้ม |
| **C. Deterministic gate ในโค้ด + คำตอบซักประวัติที่ประกอบจากรายการที่ระบบตรวจได้ (เลือก)** | **บังคับได้ 100%**, คำถามครบตาม pattern เสมอ, **ไม่ retrieve -> เร็ว (0.8-2.9 วินาที)**, LLM ใช้แค่เขียน "สรุปอาการ" 1 call เบา | ต้องมีทางออกให้ผู้ใช้ (สั่งให้ตอบเลย / เคสที่วินิจฉัยมาแล้ว) | **Best** |
| D. Refactor ทั้ง gateway ใหม่ | สะอาด | เสี่ยงทำของเดิมที่ดีอยู่แล้วพัง (ผิด constraint ข้อ 2) | ไม่ทำ |

**หลักที่ใช้ตลอดรอบ:** ต่อยอดจากโมดูลเดิม (`symptomatic_gateway.py`) เพิ่มเป็นชั้นใหม่ ไม่รื้อของเดิม และทุกชั้นเสริมอยู่ใน `try/except` -- error ใดๆ จะไม่ทำให้คำตอบหลักล้ม

## 5. สิ่งที่ทำ (รายละเอียด)

### 5.1 History-taking Gate -- "ไม่ครบ ไม่ตอบ" (หัวใจของรอบนี้)
- `history_checklist()` ตรวจตาม pattern ของผู้ใช้ครบทุกข้อ: **Who - Age - (Weight เด็ก ≤12 ปี) - What(ไข้) - Severity - When - Any treated - Allergy - Comorbidity**
  โดย Severity รวม **ลักษณะน้ำมูก (ใส/ข้นเหนียว), ลักษณะการไอ (แห้ง/มีเสมหะ)** และในเคสเจ็บคอรวม **เกณฑ์ Centor ที่ยังไม่ทราบ** (มีไอไหม, ทอนซิล, ต่อมน้ำเหลือง)
- `should_ask_first()` -> ถ้ายังขาดข้อใดข้อหนึ่ง = **ตอบด้วยการซักประวัติก่อน** โดย `generate_answer()` / `generate_answer_stream()` **ไม่ retrieve และไม่แนบ Context**
- โครงคำตอบ (ประกอบแบบ deterministic ทุกส่วน ยกเว้น "สรุปอาการ" ที่ให้ LLM เรียบเรียง 1 call):
  1. `เคสผู้ป่วยใหม่ (ประเภท 2) และ ข้อมูลไม่ครบ (ประเภท 4)` + บอกว่าขาดอะไรบ้าง
  2. **1. สรุปอาการ**
  3. **ข้อมูลที่ต้องซักเพิ่มเติมก่อนสรุปการรักษา:** -- ทุกข้อมี **เหตุผลทางคลินิกกำกับ** (คำถาม -- เหตุผล)
  4. **สรุป:** เมื่อได้ข้อมูลแล้วจะช่วยให้สรุปอะไรได้ดีขึ้น (ปรับตามเคส: Centor / เกณฑ์ไซนัส / คำนวณขนาดยาตามน้ำหนัก) + "ถ้าไม่ทราบ แจ้งได้ ผมจะประเมินจากข้อมูลที่มี"
- **เทิร์นถัดไป (ผู้ใช้ตอบคำถาม)**: `_pending_ask_case()` จับได้ว่าคำตอบก่อนหน้าเป็นการซักประวัติ -> **รวมข้อความเคสเดิม + คำตอบใหม่เป็นเคสเดียว**
  ใช้ค้น Context (สำคัญมาก -- ถ้าค้นด้วยข้อความสั้นๆ อย่างเดียวจะได้ Context ไม่ตรง) แล้ว **ตอบเต็ม 5 ขั้นเป็นประเภท 2 ห้ามถามซ้ำ** (`post_ask_note()`)
- **ไม่ถามวน**: ถามได้รอบเดียวต่อเคส; ข้อที่ผู้ใช้ยังไม่ตอบ -> เสนอยาแบบมีเงื่อนไข ("ถ้า... แนะนำ...")
- **ข้อยกเว้นที่ตอบทันที**: ผู้ใช้ระบุการวินิจฉัยมาแล้ว (เช่น Hard1 "Streptococcal pharyngitis ชัดเจน") หรือสั่งว่า "ข้อมูลมีเท่านี้/ประเมินจากข้อมูลที่มีได้เลย"
- **ขึ้นเคสใหม่ระหว่างรอข้อมูล** (คำว่า "อีกเคส" หรืออายุไม่ตรงกับเคสที่ค้างอยู่) -> ถือเป็นเคสใหม่ ไม่ใช่คำตอบของคำถามเดิม

### 5.2 Modified Centor แบบ deterministic (`centor_assessment()` / `centor_note()`)
- คิดคะแนนรายข้อจากข้อความจริง (รองรับคำปฏิเสธไทย เช่น "ไม่มีภาวะต่อมน้ำเหลือง...โต", "ตรวจไม่พบ tonsillar exudate")
- ข้อที่ผู้ใช้ไม่ได้บอก = **"ยังไม่ทราบ" (ไม่ใช่ 0 และห้ามเดา)** + แสดง "คะแนนรวมจากข้อที่ทราบ" และ "ถ้าข้อที่ไม่ทราบเป็นบวกทั้งหมด อาจได้ถึง N"
- ส่งผลลัพธ์เข้า user message แล้วสั่งใน SYSTEM ว่า **ห้ามรวมเลขใหม่/ห้ามให้คะแนนข้อที่ยังไม่ทราบ/ห้ามเขียนคำว่า "สมมติฐาน"** และให้อ้าง `[Ref: AAFP, หน้า 4]`
- เคสที่ผู้ใช้ระบุวินิจฉัยมาแล้ว -> ไม่ต้องทำตาราง Centor ใหม่ และ **ห้ามสมมติอาการประกอบของโรค** ในหัวข้อสรุปอาการ

### 5.3 ยาตามอาการ: GLOBAL vs DETAIL + ตัวเลือกครบและมีลำดับ
- `symptomatic_depth()` ตัดสินระดับรายละเอียดจากตัวเคส:
  - **GLOBAL** (เคสทั่วไป ไม่มีโรคร่วม/ภาวะพิเศษ): เขียนเป็นหมวดตามอาการ ขึ้นต้นด้วยแนวทางรวม + ทางเลือกที่ไม่ใช้ยา แล้วตามด้วยชื่อยา + ขนาดสั้นๆ
    (เช่น "กลั้วคอด้วยน้ำเกลืออุ่น หรือใช้ยาพ่นบรรเทาอาการเจ็บคอ เช่น ...") -- ไม่ลงรายละเอียดรายตัว
  - **DETAIL** (โรคร่วม/ตั้งครรภ์/ไต/ตับ/ยาเดิมไม่ได้ผล/ผู้ใช้ขอดูตัวเลือกยา): ลงรายตัว (เหมาะกับใคร + ช่วงขนาด + ขนาดสูงสุด + ข้อควรระวังที่ตรงเคส)
- **ยกเลิกเพดาน "2-4 ตัวต่อกลุ่ม"** -> เสนอ **ทุกตัวที่เหมาะและถูกต้อง** โดยจัดลำดับใน Catalog เป็น
  `[ยาหลัก] -> [ทางเลือกในกลุ่ม เช่น NSAIDs] -> [ผลิตภัณฑ์/สูตรผสม/รูปแบบอื่น] -> [ตำรับยาน้ำ/สมุนไพร]`
- ยาที่มีในตารางแต่ **ไม่ใช่ตัวเลือกทั่วไปของ URI** (Aspirin, Piroxicam, Celecoxib, Etoricoxib, Diphenhydramine, Cyproheptadine) ถูกกันไว้ไม่ให้แนะนำ
  เว้นแต่ผู้ใช้ขอดูทั้งหมด; **Aspirin ถูกตัดออกในเด็กเสมอ (Reye's syndrome)**
- ยาแก้แพ้: **รุ่นที่ 2 (ง่วงน้อย) ขึ้นก่อน** (Cetirizine, Loratadine, Fexofenadine, Levocetirizine, Desloratadine, Bilastine) แล้วตามด้วยรุ่นที่ 1 พร้อมป้าย "เหมาะน้ำมูกใสเหลว แต่ง่วง"

### 5.4 ชื่อหมวดตามรูปแบบยา (ยาพ่นคอ / ยาอม / ยากลั้วคอ)
- อ่าน "รูปแบบ" ของยาทุกตัวจากตาราง Dose แล้วแสดงใน Catalog เป็น `[รูปแบบ: ยาพ่นคอ]` พร้อม `[ตัวยา/สารสำคัญ: ...]`
- **Gateway ตรวจซ้ำหลังโมเดลตอบ** (`fix_form_labels()`): ถ้าหัวข้อเขียน "ยาอม:" แต่รายการใต้หัวข้อเป็นยาพ่น/ยากลั้วคอ ระบบแก้ชื่อหมวดให้ตรงอัตโนมัติ
  และถ้ามีหลายรูปแบบในหัวข้อเดียวจะเขียนเป็น "ยาพ่น/ยาอมบรรเทาอาการเจ็บคอ" -- ทำงานทั้ง non-stream และ streaming (กันบล็อกไว้จนเห็นรายการยาครบก่อนส่ง)

### 5.5 Expert Opinion -- Highlight ให้เห็นชัดว่าเป็น "การปฏิบัติจริง" (ฝั่งเว็บ)
- SYSTEM บังคับรูปแบบ: ขึ้นหัวข้อ `**ในทางปฏิบัติจริง (บริบทร้านยาไทย):**` + ทำ **ตัวหนาที่ประโยคชี้ขาด** (จ่าย/ไม่จ่าย, ชื่อยา+ขนาด+ระยะเวลา)
  และ **ต้องอยู่ในหัวข้อ 3a ต่อจากคำแนะนำตาม Guideline ห้ามยกไปท้ายคำตอบ**

## 8. ข้อจำกัด / ความเสี่ยงที่เหลือ
1. **LLM ยังมีความไม่แน่นอนตามธรรมชาติ** -- เคสที่เคยแกว่ง (opt-D2) แก้ด้วยกฎ "เอ่ยยาปฏิชีวนะต้องมีขนาดเสมอ" แล้ว (ข้อ 6.3) แต่ยังควรให้อาจารย์
   spot-check เคสเด็ก AOM / เคสที่ Guideline เปิดทางเลือกเฝ้าระวังอาการเพิ่ม
2. **การซักประวัติเข้มขึ้นทำให้เกือบทุกเคสต้องมี 2 เทิร์น** -- เป็นไปตามที่ผู้ใช้สั่ง แต่ถ้าหน้างานอยากได้เร็ว ผู้ใช้พิมพ์ว่า "ข้อมูลมีเท่านี้ ประเมินจากข้อมูลที่มีได้เลย" จะข้ามการถามได้ทันที
3. **การสกัดอาการยังเป็น rule-based ภาษาไทย** -- วลีแปลกๆ อาจตรวจพลาด (บันทึกกำกับให้ LLM ยึดข้อความผู้ใช้เป็นหลักเสมอ)

5. **ข้อมูลหญิงตั้งครรภ์/ให้นมบุตร ไม่มีในตาราง Dose** -> ยังต้องแยกเป็น "ข้อมูลนอกคู่มือ" เหมือนเดิม
