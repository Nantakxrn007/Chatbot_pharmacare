## 2. ตรวจของเดิมก่อนแก้ (อ่านอย่างเดียว) -- ยืนยันสาเหตุจริงทั้ง 3 ข้อ

รันเคสทั้งสามผ่านชั้น gateway แบบ deterministic (ไม่เรียก LLM) บนโค้ดเดิม ได้ผลตรงกับที่อาจารย์เจอทุกข้อ:

| เคส | ผลของโค้ดเดิม | Root cause (บรรทัดจริง) |
|---|---|---|
| 1 | `plan["antihistamine"] = ('avoid', 'น้ำมูกข้นเหนียว -- ยาแก้แพ้ (โดยเฉพาะรุ่นที่ 1 ...)')` | `plan_classes()` ตัดสิน **ทั้งกลุ่มยา** เป็นค่าเดียว (fit/conditional/avoid) ไม่มีกลไก "กลุ่มใช้ได้ แต่บางตัวในกลุ่มไม่เหมาะ" -> `build_catalog()` ยก **ทุกตัวในกลุ่ม** ไปอยู่ใต้หัวข้อ "ไม่เหมาะกับเคสนี้" และ `gate_dose_chunks()` ตัด chunk ของ Cetirizine/Loratadine ทิ้งจาก Context ด้วย -- โมเดลจึงไม่มีทางเสนอรุ่นที่ 2 ได้เลย |
| 2 | เหตุผลข้อแพ้ยาลงท้ายด้วย `"...ใช้ยากลุ่ม cephalosporin แทนได้หรือไม่"` | ข้อความ hard-code อยู่ใน `history_checklist()` (คำถาม+เหตุผลของเทิร์นซักประวัติเป็น deterministic ทั้งหมด) -- และยังมีจุดอื่นที่ยกตัวอย่างยาในเหตุผลอีก (โรคประจำตัว -> "ยาแก้คัดจมูกในความดันสูง, NSAIDs ในโรคไต", AOM -> "เคยได้ amoxicillin ใน 30 วัน") |
| 3 | `centor_assessment()` -> `applicable: True`, ถามต่อ "มีไอไหม / ต่อมน้ำเหลือง" โดยอ้างว่าเป็นเกณฑ์ Centor | ประตูเดียวของ Centor คือ `if not f.get("sore_throat"): return None` -- เคส laryngitis มี "เจ็บคอ/เยื่อบุคอแดง" จึงติด `sore_throat=True` แล้วเข้าเกณฑ์ไปโดยปริยาย |

**ตรวจ Context จริงว่า AAFP พูดว่าอย่างไร (`rag/data/AAFP.md`)**
- หน้า 4: *"...recommend using the modified Centor criteria **when evaluating patients with pharyngitis** to determine the likelihood of group A beta-hemolytic streptococcal infection"* -> **Centor ผูกกับ pharyngitis เท่านั้น**
- TABLE 1: `Laryngitis | Hoarse voice, sore throat, nasal congestion, fever | **Supportive care**` (ไม่มี Centor, ไม่มี ATB)
- หัวข้อ Laryngitis: *"Antibiotics in the treatment of laryngitis should be avoided."*
-> การตัด Centor ออกจากเคส laryngitis **เป็นไปตาม Context ตรงตัว ไม่ใช่การเดา**

## 3. สิ่งที่ทำ (แก้เฉพาะจุด ไม่ refactor)

### 3.1 แก้ข้อ 1 -- ยาแก้แพ้: แยก "รุ่นที่ 1" ออกจาก "ทั้งกลุ่ม"

เพิ่ม **status ใหม่ `partial`** (กลุ่มยังใช้ได้ แต่บางตัวในกลุ่มไม่เหมาะ) แทนที่จะเหมาเป็น `avoid` ทั้งกลุ่ม:

| จุดที่แก้ | เดิม | ใหม่ |
|---|---|---|
| `plan_classes()` (น้ำมูกข้นเหนียว) | `("avoid", "ยาแก้แพ้ ... ไม่เหมาะ")` | `("partial", "รุ่นที่ 1 ไม่เหมาะทุกตัว (รายชื่อดึงจากตารางจริง) ... **รุ่นที่ 2 ยังใช้ลดน้ำมูกได้** ควบคู่กับล้างจมูกด้วยน้ำเกลือ")` |
| `class_drug_block()` **(ฟังก์ชันใหม่ 8 บรรทัด)** | -- | คืนเหตุผลกันเฉพาะ "ตัวยา" ที่ไม่เหมาะในกลุ่มนั้น (กฎเดียวตอนนี้: `first_gen` + น้ำมูกข้นเหนียว + ไม่ใช่เคสภูมิแพ้) |
| `build_catalog()` | ทั้งกลุ่มไปอยู่ใต้ "ไม่เหมาะกับเคสนี้" | รุ่นที่ 2 อยู่ใน `[ยาหลัก]` พร้อมขนาด+หน้า, รุ่นที่ 1 ไปอยู่บรรทัด "มีในตารางแต่ไม่แนะนำในเคสนี้ -- เหตุผล ..." |
| `gate_dose_chunks()` | ตัด chunk ยาแก้แพ้ทั้งกลุ่ม | ตัดเฉพาะตัวที่ถูกกันระดับตัวยาในทุกกลุ่มที่เกี่ยวข้อง |
| SYSTEM prompt (หลักเภสัชวิทยา) | "น้ำมูกข้นเหนียว -> ไม่ใช้ Antihistamine รุ่นที่ 1 -> แนะนำล้างจมูก" | เพิ่ม **"รุ่นที่ 2 ยังใช้ได้"** + **ห้ามเขียนเหมารวมทั้งกลุ่ม และห้ามใส่ Cetirizine/Loratadine ไว้ในรายการ 'ไม่เหมาะกับเคสนี้' เด็ดขาด** |
| SYSTEM prompt (ใหม่) | -- | **กฎสมดุล**: ถ้าคำตอบเอ่ยชื่อยาว่า "ไม่เหมาะ" ต้องเอ่ยชื่อตัวเลือกที่ "ใช้ได้" ในกลุ่มเดียวกัน พร้อมขนาด + `[Ref]` ในคำตอบเดียวกันเสมอ (ห้ามบอกแต่ตัวที่ห้ามแล้วผลักตัวที่ใช้ได้ไปให้ถามต่อ) |

> กฎนี้เป็น **ความรู้ระดับกลุ่มยา ไม่ใช่ hard-code รายเคส** -- ใช้กับทุกเคสน้ำมูกข้นเหนียว/ไซนัสอักเสบโดยอัตโนมัติ
> และ **ไม่กระทบเคสน้ำมูกใส** (รุ่นที่ 1 ยังถูกเสนอเป็นตัวเลือกตามเดิม -- ทดสอบแล้วในข้อ 4)

### 3.2 แก้ข้อ 2 -- ขั้นซักประวัติไม่ยกตัวอย่างยา

แก้ข้อความ deterministic ใน `history_checklist()` / `history_gaps()` + เพิ่มกฎบังคับใน SYSTEM prompt (กัน LLM เติมเอง):

| คำถาม | เหตุผลเดิม | เหตุผลใหม่ |
|---|---|---|
| ประวัติแพ้ยา | "...ชนิดของอาการแพ้เป็นตัวกำหนดว่าใช้ยากลุ่ม **cephalosporin** แทนได้หรือไม่" | "...**ชนิดและความรุนแรงของอาการแพ้เป็นตัวกำหนดว่าจะเลือกยาปฏิชีวนะทางเลือกกลุ่มใดได้บ้าง**" |
| โรคประจำตัว (ผู้ใหญ่) | "...เช่น **ยาแก้คัดจมูก**ในความดันสูง, **NSAIDs** ในโรคไต/แผลในกระเพาะ/หอบหืด" | "...**เพราะโรคประจำตัวบางอย่างเป็นข้อห้ามหรือต้องปรับขนาดยา**" |
| โรคประจำตัว (เด็ก) | "...เช่น **NSAIDs** ในหอบหืด และผลิตภัณฑ์บางชนิดในผู้ที่เป็น G6PD" | "...**ซึ่งโรคประจำตัวบางอย่างเป็นข้อห้ามของยาบางกลุ่ม**" |
| ยาที่ใช้มาก่อน (เคส AOM) | "...ถ้าเคยได้ **amoxicillin** ใน 30 วัน จะเปลี่ยนยาตัวแรก" | "...**ยาปฏิชีวนะที่เคยได้ภายใน 30 วันมีผลต่อการเลือกยาตัวแรก**" |
| ลักษณะน้ำมูก | "...น้ำมูกข้นเหนียวไม่ควรใช้ **antihistamine รุ่นที่ 1** ... ควรล้างจมูกแทน" | "...น้ำมูกใสเหลว/ไหลเป็นสาย กับน้ำมูกข้นเหนียว **ใช้ยาคนละแบบกัน** และถ้าข้นเหนียวต้องเน้นล้างจมูกด้วยน้ำเกลือร่วมด้วย" |

**กฎใหม่ใน SYSTEM prompt:** ในทุกคำถาม/เหตุผลของการซักประวัติ (รวมหัวข้อ "ข้อมูลที่ควรซักเพิ่มเติม") **ห้ามเอ่ยชื่อยาเฉพาะตัวหรือชื่อกลุ่มยาทางเลือกเป็นตัวอย่าง** พร้อมเหตุผล (ยังไม่ได้ตัดสินใจเลือกยา + ยกมาไม่ครบ = bias) และระบุ **ข้อยกเว้นเดียว** คือคำถามที่ตัวคำถามเองคือการถามชื่อยาของผู้ป่วย และการอธิบาย *กลไก* ที่เป็นสาระของคำถามนั้น (ไอแห้ง vs ไอมีเสมหะ)

### 3.3 แก้ข้อ 3 -- Centor ใช้เฉพาะ pharyngitis

เพิ่มฟังก์ชัน **`centor_scope(f)` (13 บรรทัด)** เป็นประตูเดียวของเกณฑ์ Centor แล้วให้ทุกจุดที่เคยเช็ค `sore_throat` เองเรียกผ่านมันแทน:

```
centor_scope(f):
  ไม่มี sore_throat            -> (False, "")            # เหมือนเดิม
  อายุ < 3 ปี                  -> (False, "child3")      # เหมือนเดิม
  hoarse=True และ **ไม่มี**สิ่งตรวจพบบ่งชี้ GABHS
  (ทอนซิลบวม/มีหนอง หรือต่อมน้ำเหลืองคอด้านหน้าโต)  -> (False, "laryngitis")   # ใหม่
  นอกนั้น                      -> (True, "")
```

- เพิ่ม `f["tonsil_finding"]` / `f["lymph_finding"]` ใน `extract_case_features()` (ใช้ regex เดิมของ Centor ไม่ได้เขียนใหม่)
- จุดที่ถูกกันทั้งหมด (5 จุด): `centor_assessment()`, `centor_note()`, คำถามซักประวัติที่อ้างเกณฑ์ Centor (ไอ/ทอนซิล/ต่อมน้ำเหลือง/อายุ/ไข้), ประโยคปิดท้ายของเทิร์นซักประวัติ (`ask_first_reply`), และ `practice_flags()` (Expert Opinion RDU)
- **แต่ยังต้องรู้ว่ามีไอไหม** -> เคสคอ/เสียงแหบที่อยู่นอกขอบเขต ยังถามคำถามเดิม แต่เปลี่ยนเหตุผลเป็น *"เพื่อประเมินอาการร่วมและเลือกยาบรรเทาอาการให้ตรง"* (ไม่อ้าง Centor)
- `centor_note()` ส่งบล็อกใหม่เข้า Context ว่า **"Modified Centor -- ไม่ต้องประเมินในเคสนี้"** พร้อมเหตุผลจาก AAFP + สั่งให้ใช้เหตุผลของ laryngitis ตรงๆ แทน
- SYSTEM prompt เพิ่มหัวข้อ **"ขอบเขตของเกณฑ์ตาม Context"** (อ้างประโยค *"when evaluating patients with pharyngitis"* ตรงจาก AAFP) + แก้อีก 3 จุดที่พูดถึง Centor ให้สอดคล้อง

### 3.4 (รอบแก้เพิ่มเติม) "เช่น <ยาตัวเดียว>" ทั้งที่มีหลายตัวเข้าข่าย

**Feedback:** หลังแก้ข้อ 3.1 แล้ว คำตอบเขียนว่า *"กลุ่มที่ไม่แนะนำ: ยาแก้แพ้รุ่นที่ 1 (**เช่น Chlorpheniramine**) ..."*

-> ผู้อ่าน bias คิดว่าห้ามแค่ CPM ตัวเดียว

| Antihistamine **รุ่นที่ 1** | **Chlorpheniramine (p1), Brompheniramine (p1), Diphenhydramine (p2), Cyproheptadine (p3), Hydroxyzine (p3)** -- **5 ตัว** | ลดสารคัดหลั่งแรงจนน้ำมูกข้นเหนียวแห้งติดในโพรงจมูก |

| Antitussive (ถ้าไอมีเสมหะ) | Dextromethorphan (p36), Levodropropizine (p37), Terco-D (p39), Strepsils dry cough (p42) | ยากดการไอขัดขวางการขับเสมหะ |

**การแก้ 4 ชั้น (ชั้นสุดท้ายเป็น deterministic จึงไม่พึ่งดวงของโมเดล):**

| ชั้น | สิ่งที่ทำ |
|---|---|
| **1. Context (data-driven)** | เพิ่ม `class_drug_names(cls, first_gen=)` ดึงรายชื่อยาของกลุ่มจาก **ตาราง Dose จริง** -> ข้อความใน `plan_classes()` ไม่ hardcode ชื่อยาอีกต่อไป (เดิมเขียนไว้แค่ 2 ตัว) ตอนนี้ขึ้นเป็น *"ยาแก้แพ้รุ่นที่ 1 ไม่เหมาะกับเคสนี้ทุกตัว ในตารางมี 5 ตัว ได้แก่ ..."* -- ถ้าตารางเพิ่ม/ลดยา ข้อความเปลี่ยนตามเอง |
| **2. Catalog** | รวมยาที่ "เหตุผลเดียวกัน" ไว้บรรทัดเดียว (เดิมไล่ทีละตัวพร้อมเหตุผลซ้ำ 5 รอบ -> โมเดลย่อเหลือตัวเดียว) + สั่งกำกับว่า **"ต้องเอ่ยชื่อให้ครบทุกตัว ห้ามยกมาแค่ตัวเดียว"** และ **"ถ้ายุบหลายหมวดมารวมบรรทัดเดียว ต้องเอ่ยชื่อของทุกหมวดที่ยุบมา"** |
| **3. SYSTEM prompt** | กฎทั่วไป **"เช่น / ได้แก่"**: ถ้ามีหลายตัวเข้าข่ายจริง ต้องเอ่ยให้ครบ -- ห้ามเขียน "เช่น \<ยาตัวเดียว\>"; ถ้ามีตัวเดียวจริงๆ ให้เขียนตรงๆ ไม่ต้องใช้คำว่า "เช่น" (ใช้กับ**ขั้นแนะนำการรักษา**เท่านั้น -- ขั้นซักประวัติยังห้ามเอ่ยชื่อยาตามข้อ 3.2) |
| **4. Post-process guard (deterministic)** | `expand_group_examples()` -- ถ้าคำตอบยังหลุดมาเป็น "ยาแก้แพ้รุ่นที่ 1 (เช่น X)" **ในบริบทเชิงลบ** (ไม่เหมาะ/ไม่แนะนำ/หลีกเลี่ยง) และทั้งบรรทัดยกชื่อยาของกลุ่มมา **ตัวเดียว** -> เติมให้ครบจากตาราง แล้วเปลี่ยนคำว่า "เช่น" เป็น "ได้แก่"; รู้จักตัวย่อหน้าร้าน (เขียน "CPM" ก็จับได้) และมี hold-back ตอน streaming ไม่ให้บรรทัดถูกหั่นกลาง |

**ทำไม guard จำกัดเฉพาะ "บริบทเชิงลบ" เท่านั้น:** การเติมชื่อยาที่ **ถูกกันออก** ให้ครบนั้นปลอดภัยเสมอ
แต่ถ้าไปเติมฝั่ง "แนะนำให้ใช้" อัตโนมัติจะอันตราย (เช่น เติม Aspirin เข้าไปในรายการ NSAIDs ของเคสเด็ก)
-> ฝั่งแนะนำให้ยึดรายการที่ Catalog คัดมาแล้วเท่านั้น

### 3.5 (พบระหว่างทดสอบ) บั๊กเลขหน้า `[Ref: Dose]` -- แก้ให้ตรงตามข้อจำกัดของโจทย์

ระหว่างรันเคสที่ 1 พบว่าคำตอบเขียน **`Ibuprofen ... [Ref: Dose, หน้า 8]`** ทั้งที่ Ibuprofen อยู่ **หน้า 10** (หน้า 8 = Paracetamol) -> กดอ้างอิงแล้วเปิดผิดยา

- **เป็นบั๊กเดิม ไม่ได้เกิดจากการแก้รอบนี้** (อยู่ใน `_line_dose_pages()` / `_last_drug_hit()` ซึ่ง diff รอบนี้ไม่ได้แตะมาก่อนหน้า) แต่เข้าข่ายข้อจำกัด *"เลขหน้าอ้างอิงห้ามโดนเด็ดขาด"* จึงแก้ให้ในรอบนี้
- **สาเหตุ:** `_last_drug_hit()` เลือก "ชื่อยาที่ยาวที่สุดในบรรทัด" (กฎที่ทำไว้ให้ชื่อผลิตภัณฑ์ชนะชื่อสามัญ) -- พอบรรทัดอธิบายยาเอ่ยชื่อยาตัวอื่นประกอบ เช่น
  `- **Ibuprofen:** เหมาะกับคนที่ใช้ Paracetamol แล้วไม่ดีขึ้น [Ref: Dose]` -> `Paracetamol` (11 ตัวอักษร) ชนะ `Ibuprofen` (9) -> chip ชี้หน้า 8
  และบรรทัดย่อย `ขนาด: ...` ที่ไม่มีชื่อยา ก็ไปหยิบหน้าเดียวกันต่อจาก window 300 ตัวอักษร
- **การแก้ (2 ฟังก์ชันใหม่ ไม่แตะกฎเดิม):**
  - `_label_drug_page(line)` -- ยาที่อยู่ **ตำแหน่งหัวข้อของบรรทัด** (`- **ชื่อยา:** ...`) คือเจ้าของ `[Ref]` บรรทัดนั้น ให้ชนะก่อนเสมอ
  - `_recent_drug_page(before)` -- บรรทัดที่ไม่มีชื่อยา (`ขนาด: ...`) ให้ไล่ย้อน **ทีละบรรทัด** หาหัวข้อยาล่าสุด แทนการเทียบความยาวข้ามบรรทัด
  - ถ้าหัวข้อไม่ใช่ชื่อยา (`ยาแก้ปวด/ลดไข้:`, `ขนาด:`) จะ fallback ไปกฎเดิมทุกประการ -> **กฎ "ชื่อผลิตภัณฑ์ชนะชื่อสามัญ" ยังทำงานเหมือนเดิม** (ทดสอบยืนยันแล้ว: `Strepsils dry cough (Dextromethorphan)` -> หน้า 42 ไม่ใช่ 36)
  - **(พบเพิ่มรอบสุดท้าย) วงเล็บที่ไล่ "ตัวยา/ส่วนประกอบ" ของผลิตภัณฑ์** -- เช่น
    `ยาสูตรผสม (เช่น Decolgen prin, TIFFY DEY (ตัวยา: Paracetamol + Chlorpheniramine + Phenylephrine))`
    กฎ "ชื่อยาวสุดชนะ" จะเลือก `Chlorpheniramine` (16 ตัวอักษร, หน้า 1) แทน `Decolgen prin` (13, หน้า 7)
    -> เพิ่มเงื่อนไข: ชื่อยาที่อยู่ **หลังคำบอกตัวยา** (`ตัวยา / ส่วนประกอบ / ประกอบด้วย / สารสำคัญ / สารสกัด`)
    เป็น "คำอธิบายส่วนผสม" ไม่ใช่ยาที่บรรทัดนั้นพูดถึง จึงตัดออกก่อนใช้กฎเดิม (ทดสอบ 7/7 รวมเคสที่ห้ามเปลี่ยน)

### 3.6 (feedback รอบสาม) หัวข้อ "กลุ่มที่ไม่เหมาะกับเคสนี้" หายไปจากคำตอบ

**Feedback:** หลังแก้ข้อ 3.1 + 3.4 แล้ว คำตอบเคสไซนัสอักเสบ **ไม่มีหัวข้อ "กลุ่มที่ไม่เหมาะกับเคสนี้" อีกเลย**
-- เหลือแค่โน้ตในวงเล็บใต้กลุ่มยาแก้แพ้ว่ารุ่นที่ 1 ไม่แนะนำ ส่วนกลุ่มที่ห้ามทั้งกลุ่ม (ยาสูตรผสม Decolgen/TIFFY,
สูตรผสม Decongestant+Antihistamine, ยาพ่นจมูกสเตียรอยด์) **หายไปทั้งหมด**

**วัดก่อนแก้:** รันเคสเดิมซ้ำ **4 ครั้ง -> มีหัวข้อนี้เพียง 1/4** (ไม่ใช่ความแกว่ง แต่เป็นพฤติกรรมใหม่ที่ถดถอยจริง)

**Root cause -- เป็นผลข้างเคียงจากการแก้ข้อ 3.1 ของรอบนี้เอง (รายงานตามจริง):**
- เดิม `plan["antihistamine"] = "avoid"` -> ยาแก้แพ้ทั้งกลุ่มอยู่ในบล็อก `■ ไม่เหมาะกับเคสนี้` ทำให้บล็อกนั้น "ใหญ่และเด่น"
  โมเดลจึงเรนเดอร์เป็นหัวข้อในคำตอบเสมอ
- พอเปลี่ยนเป็น `partial` ยาแก้แพ้ย้ายออกจากบล็อกนั้นไปอยู่เป็น "โน้ตในวงเล็บ" ใต้กลุ่มที่แนะนำแทน
  -> โมเดลถือว่า "บอกข้อห้ามแล้ว" แล้วข้ามหัวข้อรวมไปเลย
- ซ้ำร้าย **กฎเดิมใน SYSTEM prompt เขียนเป็นเงื่อนไข**: *"ห้ามแนะนำยาในกลุ่มที่ Catalog ระบุว่าไม่เหมาะ
  (**ถ้าจะกล่าวถึง** ให้บอกสั้นๆ ว่าไม่แนะนำเพราะอะไร)"* -- คือไม่เคยบังคับมาก่อน ระบบพึ่งพฤติกรรมของโมเดลล้วนๆ

**การแก้ 3 ชั้น:**

| ชั้น | สิ่งที่ทำ |
|---|---|
| **1. Catalog header** | จาก *"ถ้าจะกล่าวถึง..."* -> **"บังคับ: ถ้าคำตอบนี้ลงรายชื่อยา ต้องปิดท้าย 3b ด้วยหัวข้อ 'กลุ่มที่ไม่เหมาะกับเคสนี้' ไล่ครบทุกหมวด หมวดละ 1 บรรทัด พร้อมชื่อยาครบทุกตัว"** |
| **2. SYSTEM prompt** | กฎบังคับเต็มรูป + ระบุชัดว่า **"การเขียนข้อห้ามแทรกในวงเล็บใต้กลุ่มยาที่แนะนำ ไม่นับว่าทำข้อนี้แล้ว"** (คนละส่วนกัน: วงเล็บ = ตัวที่ถูกคัดออกจากกลุ่มที่แนะนำ / หัวข้อนี้ = กลุ่มที่ห้ามทั้งกลุ่ม) + เหตุผลว่าเภสัชกรต้องรู้ว่า **อะไรห้ามจ่าย** ไม่ใช่รู้แค่ว่าจ่ายอะไรได้ |
| **3. Deterministic backstop** | `avoided_groups()` / `missing_avoided_block()` / `ensure_avoided_section()` -- ถ้าคำตอบลงชื่อยาแล้ว (มี `[Ref: Dose, หน้า N]` ≥ 2 จุด) แต่ยัง **ไม่เอ่ยถึงหมวดที่ห้ามเลย** ระบบเติมหัวข้อให้เอง: non-stream แทรกก่อนบรรทัดเชิญถามต่อ/ตารางสรุป/หัวข้อ 4, streaming ต่อท้ายแล้วส่งเป็น chunk เพิ่ม (แทรกกลางข้อความที่สตรีมไปแล้วไม่ได้) |

**เติมเฉพาะ "หมวดที่ยังไม่ถูกเอ่ยถึงเลย"** -- ถ้าโมเดลเขียนครบเองแล้วจะไม่แตะ และ **ไม่เติมในคำตอบแรก**
ที่ยังบอกแค่ชื่อกลุ่มยา (คงสไตล์ 2 ขั้นเดิมของระบบ)

### 4.5 ผลของการแก้บั๊กเลขหน้า (ข้อ 3.5) -- วัดเป็นตัวเลข

เทียบตรรกะ **เก่า vs ใหม่** บน `[Ref: Dose]` ทุก chip จากคำตอบจริงทั้งหมด:

## 6. ข้อจำกัด / ความเสี่ยงที่เหลือ

1. **การตัดสินว่า "เคสนี้เป็น laryngitis หรือ pharyngitis" ใช้ rule-based** -- เกณฑ์คือ *มี "เสียงแหบ/สายเสียงอักเสบ"* และ *ไม่มีสิ่งตรวจพบบ่งชี้ GABHS (ทอนซิลบวม/มีหนอง, ต่อมน้ำเหลืองคอด้านหน้าโต)* ถ้าอาจารย์เห็นว่าควรใช้เกณฑ์อื่น แก้ได้ที่ `centor_scope()` **จุดเดียว** -- ทุกจุดที่ใช้ Centor อ่านจากฟังก์ชันนี้หมดแล้ว
2. **เคสที่เป็นทั้ง laryngitis และ pharyngitis พร้อมกัน** -- ตอนนี้ถ้ามีสิ่งตรวจพบ GABHS ร่วม ระบบจะยังใช้ Centor (เผื่อความปลอดภัยฝั่งไม่พลาด strep) ควรให้อาจารย์ยืนยันว่านี่คือพฤติกรรมที่ต้องการ
3. **กฎยาแก้แพ้รุ่นที่ 1 vs 2 อิงคอลัมน์ `first_gen` ของ formulary** ซึ่งมาจากรายชื่อตัวยาใน `_FIRST_GEN_AH` -- ถ้าตาราง Dose เพิ่มยารุ่นที่ 1 ตัวใหม่ ต้องเพิ่มชื่อในลิสต์นี้ (1 บรรทัด) แล้วข้อความ "ได้แก่ ..." ทุกจุดจะอัปเดตตามเอง (ดึงผ่าน `class_drug_names()`)
4. **ตัวเติมชื่อยาอัตโนมัติ (`expand_group_examples`) ครอบเฉพาะกลุ่ม "antihistamine รุ่นที่ 1" ในบริบทเชิงลบ** -- กลุ่มอื่นอาศัยกฎใน SYSTEM prompt อย่างเดียว เพราะการเติมอัตโนมัติฝั่ง "แนะนำให้ใช้" มีความเสี่ยงด้านความปลอดภัย (เช่น Aspirin ในเด็ก) ถ้าอาจารย์เจอกลุ่มไหนยกไม่ครบบ่อยๆ แจ้งได้ จะเพิ่มกฎ deterministic รายกรณี
5. **Backstop หัวข้อ "กลุ่มที่ไม่เหมาะกับเคสนี้" ตอน streaming จะไปอยู่ท้ายคำตอบ** (ไม่ใช่ท้ายหัวข้อ 3b เหมือนฝั่ง non-stream) เพราะแทรกกลางข้อความที่สตรีมออกไปแล้วไม่ได้ -- เกิดเฉพาะกรณีที่โมเดลลืมเขียนเองเท่านั้น ถ้าอาจารย์เห็นว่าตำแหน่งนี้อ่านแล้วสะดุด บอกได้
6. **LLM ยังมีความไม่แน่นอนตามธรรมชาติ** -- ข้อตรวจเชิงโครงสร้าง/เลขหน้า/ชื่อยาที่ไม่แนะนำ/หัวข้อกลุ่มที่ห้าม เป็น deterministic แล้ว แต่ "การตัดสินใจว่าเทิร์นนี้ควรลงชื่อยาหรือยัง" ยังแปรตามรอบ -- วัดได้ 1 ครั้ง (REG3, ข้อ 4.1.1) รันซ้ำผ่าน 3/3 หากเจอบ่อยขึ้นจะทำ deterministic gate ให้เทิร์น "ขอชื่อยา" เหมือนที่ทำกับ Centor/ซักประวัติ
7. **ยังไม่ได้แก้กฎเรื่อง "ไม่ยกตัวอย่างยา" ในหัวข้ออื่นนอกขั้นซักประวัติ** -- ตั้งใจไม่แตะ เพราะขั้นแนะนำการรักษา **ต้อง** มีชื่อยาและขนาดยา (ตาม feedback รอบก่อนๆ)

## 7. Next Steps (ไม่ควรมีปัญหาเพิ่ม)

1. ให้อาจารย์ลองยิงเคสจริงหน้าร้านชุดเดียวกับรอบนี้ โดยเฉพาะ **เคสน้ำมูกข้นเหนียว** (ดูว่าเสนอรุ่นที่ 2 ตัวไหนบ้าง ตรงกับที่ต้องการไหม) และ **เคสเสียงแหบ** (ดูว่าเหลือคำถามครบพอไหมหลังตัดคำถาม Centor ออก 2 ข้อ)
2. ถ้าอาจารย์เห็นว่าเคส **"น้ำมูกข้นเหนียว"** ควรเน้นล้างจมูกเป็นหลักแล้วค่อยเสนอรุ่นที่ 2 เป็นตัวเสริม (หรือกลับกัน) ปรับลำดับได้ที่ข้อความ reason ของ `plan_classes()` บรรทัดเดียว ไม่กระทบตรรกะ
3. **ข้อเสนอ:** นำชุดตรวจ invariant ของรอบนี้ (Centor scope / รุ่นที่ 2 ไม่ถูกเหมารวม / ซักประวัติไม่มีชื่อยา / เลขหน้า Dose) เข้า repo เป็นสคริปต์ regression ถาวร เพื่อให้รอบถัดๆ ไปตรวจซ้ำได้อัตโนมัติ (ตอนนี้อยู่นอกโปรเจกต์ตามข้อกำหนด "ลบไฟล์ที่ไม่เกี่ยวข้อง")
4. ค้างจากรอบก่อน (ยังไม่ทำ เพราะโจทย์รอบนี้ห้ามแตะจุดที่ไม่ได้บอก): เปลี่ยน `PDF_FILENAMES["AAFP"]` เป็น `AAFP 2022_new.pdf`, และให้ทีม Ingestion เพิ่มคอลัมน์ Pregnancy/Lactation
